# ADR-0038 — Intrinsic-liveness gate: force UNKNOWN on a frozen backing (in-hash, disabled-default)

- **Status:** Accepted (2026-07-17). Built on `landing/v2-port` in the staged (unpublished) **methodology 0.7.0** bundle, **DISABLED by default**, 1:1 + adversarially validated, **NOT deployed**. This is the in-hash close of the intrinsic-liveness gap; the out-of-hash advisory (ADR-0037 badge + the self-audit flag/epoch-lag gauges) is the honest interim.
- **Relationship to ADR-0037:** ADR-0037 makes a frozen backing *visible* (an amber badge, gauges, alerts) without touching a verdict. ADR-0038 makes it *move* the verdict — force UNKNOWN. It is the verdict-affecting twin, gated behind an opt-in flag exactly like the depth gate (ADR-0034/0026).
- **Decision owner:** founder (chose: into 0.7.0 not a new bump; staleness-only signal; enable + calibrate at deploy). Kept disabled until then.

## Context

Pegana's intrinsic side has no liveness gate: the engine's staleness check is timestamp-only and the Sanctum/SPL sources re-stamp `ts=now()` every poll, so a **frozen-but-served backing reads as a confident PEGGED** (the 2026-04-01 dSOL failure mode). ADR-0037 surfaced this as an advisory; the *real* close is to force UNKNOWN — but that changes verdicts + the receipt hash, so it must be irreversible-once-published (methodology + CLI-first re-release) and can't flip on silently.

## Decision

Add a force-UNKNOWN override on a frozen `intrinsic_stale: bool`, **disabled by default**, byte-exact when off.

- **The gate (methodology):** `intrinsic_liveness_gate_violated(inputs.intrinsic_stale)` joins the override branch in `rederive` (and the engine + the xtask runner) alongside premium/discount sanity + the Pyth conf gate — any true → UNKNOWN. New `STATE_REASON_INTRINSIC_LIVENESS`.
- **The frozen signal:** a new `InputsFrozen.intrinsic_stale` with `#[serde(default, skip_serializing_if = "is_false")]`. **This is the byte-exactness mechanism:** the canonical hash is RFC-8785 JCS via serde, so a `false` value is OMITTED → every pre-existing receipt + the backtest golden hash byte-identically, and old receipts still deserialize (serde default). A `true` value IS hashed, so a stale-forced UNKNOWN is tamper-evident + re-derivable.
- **Disabled-default (the depth-gate/ADR-0034 pattern):** the ENGINE only sets `intrinsic_stale=true` when `INTRINSIC_LIVENESS_GATE` is enabled AND the signal says stale. Disabled (default) → the engine never reads the signal, never sets the field → the field is omitted → verdicts + hashes are **provably unchanged**. The flag lives in the engine (freezing); `rederive` keys off the frozen field, so a receipt always re-derives to the verdict it froze.
- **The plumbing (the coverage split, ADR-0037 §Open):** a new `intrinsic_liveness(asset, stale, reason, detail, updated_at)` table (migration 0068), upserted every poll by the indexer:
  - `lst_directory_audit` → sanctum_lst rows, `stale = flags.stale AND rate==ratePrev` (`reason='directory_stale'`, `directory_gate_stale()`) — Sanctum has no on-chain epoch, so the directory's own liveness call is the signal, but the raw flag over-flags (see §Calibration), so it's CORROBORATED by the rate actually being frozen.
  - `spl_stake_pool` → SplStakePool rows (jitoSOL et al.), `stale = epoch_lag >= 2` (`reason='epoch_lag'`) — these aren't in the directory, but the on-chain `last_update_epoch` is.
  - `hylo` → hyUSD + xSOL rows, `stale = total_sol_cache epoch_lag >= 2` (`reason='epoch_lag'`) — both read `total_sol`; sHYUSD is excluded (its rate is pool-balance-based, independent of that cache). Partially masked (reserve_usd tracks live SOL price) but a frozen SOL quantity is still wrong.
  - `perena` → USD\* rows, `stale = nav_accrual_stall` (`reason='nav_accrual_stall'`) — no on-chain epoch/timestamp, but USD\* is a yield vault whose NAV should keep moving, so a NAV flat across a densely+continuously observed 12h window (calibrated: 21d prod max healthy flat ~3h35m) is the frozen-crank signal. Measured from window stats — `distinct_navs <= 1` (flat) AND `oldest_age >= 90% of window` (actually spanned, not a cold start) AND `max_gap <= 5 min` (no polling OUTAGE mistaken for a freeze); anything thin/young/gappy fails OPEN (see §Open #4).
  The engine reads the latest row per asset (only when enabled), **freshness-guarded**: a row older than `INTRINSIC_LIVENESS_FRESHNESS_SECS` (default 3600s) is ignored → **fail-open** (a dead liveness SOURCE must not force UNKNOWN; the engine's own 600s staleness gate already owns a dead intrinsic). A read error → false.
- **Scope = staleness only** (founder call): `flags.stale` / `epoch_lag>=2`. `dead`/`deprecated` (an LST being wound down, not a frozen value) stay advisory (the badge), never force a verdict — avoids a false-UNKNOWN on a still-healthy deprecated LST.
- **Version = into 0.7.0** (founder call): the gate rides the same unpublished staged 0.7.0 (conf-gate + depth-gate + intrinsic-liveness), since nothing is published yet (crates.io tops at 0.6.1). The CLI stays `pegana-replay 0.5.0`.

## Addendum (2026-10-24): version note

`intrinsic_stale` is a hashed input that shipped inside 0.7.0 without a bump. The published `pegana-replay 0.5.2` does not know the field, so it would report a "sha256 mismatch" for a receipt that carries `intrinsic_stale = true`. No such receipt exists while the gate is off. ADR-0046 bumps the methodology to 0.8.0, after which a 0.5.2 verifier reports VERSION_MISMATCH with an install hint instead.

## Validation

- **methodology:** 116 tests. The byte-exactness invariant is a DEDICATED test (`intrinsic_stale_false_is_omitted_from_canonical_hash`): `false` is absent from the JCS, `true` present. `rederive` gate tests: stale→UNKNOWN, inert-when-false across classes.
- **xtask:** the runner fires the gate (matches the engine branch); a stale-frozen tick → UNKNOWN + self-verifies via `rederive`; **the backtest golden is byte-exact** (`run_case_produces_deterministic_output` — existing fixtures carry `intrinsic_stale=false` → omitted).
- **engine:** disabled-default → `EngineState::new` sets `enabled=false` → `try_recompute` never reads the DB, never sets the field. Compiles clean; the full `cargo test --workspace` is green with zero verdict/hash change.
- **CLI:** the verifier (pegana-replay, embeds methodology 0.7.0) deserializes + re-derives receipts with/without the field (18 unit + 14 integration green).
- **Provably inert:** disabled → byte-identical receipts + identical verdicts, proven at the hash level (JCS omission) not just the verdict level.

## Rollout — code-complete but ships INERT

- No behavior change on deploy while `INTRINSIC_LIVENESS_GATE` is unset. Ships with the 0.7.0 methodology/CLI release + migration 0068 + the indexer rebuild (which starts populating `intrinsic_liveness`, observe-only). To ENABLE: calibrate against prod (§Open), then set the env — no new code deploy needed.
- Rollback: unset the env (instant, no redeploy) → back to inert. The additive field + table are harmless when unused.

## Calibration — LIVE against the directory (2026-07-17, no prod needed)

Fetched lst-directory.com and cross-checked our 41 tracked `sanctum_lst` mints against `flags.stale`:

| Signal | Result | Action |
|---|---|---|
| `flags.stale` raw, whole directory | **8/244** rows flagged (3.3%) — all obscure dust LSTs (cySOL, fmSOL, sharkSOL…) | — |
| `flags.stale` ∩ OUR tracked 41 | **1** — `sharkSOL` (active, NOT monitoring_only, TVL **$141**) | ⚠️ |
| sharkSOL's actual rate | **ADVANCING** — 1.057490 > ratePrev 1.057279 | **false-positive** |

**The finding:** the directory's `flags.stale` is NOT a clean "backing frozen" indicator — it flagged sharkSOL (a rate-advancing $141 dust LST we track) as stale. Enabling the gate on the raw flag would have **falsely forced sharkSOL → UNKNOWN**. **Fix (founder call):** the gate signal is now `flags.stale AND rate==ratePrev` (`directory_gate_stale()`) — corroborate the flag with a CONFIRMED non-advancing rate. sharkSOL (rate advancing) no longer trips; a genuinely-frozen LST (flag + `rate==ratePrev`) still does. `None` (rate/ratePrev absent) fails OPEN. The advisory badge/gauge keep the raw flag; only the gate signal is corroborated. This is exactly the "provably-inert-on-healthy" discipline of ADR-0032/0035 — calibration caught a false-positive before the gate ever fired.

Still to confirm post-deploy: the SplStakePool + Hylo `epoch_lag>=2` distributions (needs a running indexer — the advisory `pegana_*_epoch_lag` gauges give it).

## Open (founder, before ENABLE)

1. **Re-run the cross-check after deploy** with the corroborated signal — expect **0** tracked assets stale on healthy operation (sharkSOL now excluded). Consider deactivating sharkSOL regardless (a $141-TVL dust LST is below any meaningful monitoring floor).
2. **Freshness window:** 3600s default — tune vs the 15-min directory + 30s SPL cadences.
3. **Never enable mid-calibration** (the standing engine rule): flip the env only during a deliberate window.
4. **Coverage blind spot — 1:1 dispositioned (2026-07-17 audit):** the gate covers 3 source types (sanctum_lst / SplStakePool / Hylo). The two uncovered sources are **NOT symmetric**, and a re-read of both decoders settled what to do with each:
   - **Perena (USD\*) — was "the live gap", NOW COVERED (`nav_accrual_stall`, `perena.rs`).** The reserve decoder (layout confirmed: discriminator·total_underlying@192·share_supply@200·share_mint@320·nav@352, `MIN_RESERVE_LEN=360`) exposes **no on-chain freshness marker** — no epoch, no `last_update_ts`, no slot (corroborated by a byte-scan of the captured 1560-byte fixture: nothing outside the four known fields reads as a plausible continuously-updated slot/timestamp). So there is no on-chain epoch to read — BUT USD\* is a **price-based monotonic-yield** vault (NAV only ticks UP as yield accrues via `updateYieldingInfo`; NOT rebasing, NOT $1-pegged), so a NAV that has **stopped advancing** is itself the frozen-backing signal, the Perena analogue of the SplStakePool `epoch_lag`. **Disposition (upgraded from "accept blind spot"): implement a data-calibrated `nav_accrual_stall` writer.** The earlier "nav-constancy = the sharkSOL trap" worry was settled EMPIRICALLY, not assumed: a read-only query over **21 days of prod history** (2026-06-27..07-18, 60,461 polls @30s, since mig 0055) shows USD\*'s NAV ticks **~every 20 min (median), p95 gap ~1h17m, MAX healthy flat ~3h35m**. So a **12h stall window is ~3.3× the observed max flat — zero false-positives in-sample** while a genuinely frozen crank still trips. The check keys off *observation stats over the window*, not a wall-clock "time since last change" (which would false-fire after a >12h indexer/DB OUTAGE — the on-chain NAV kept accruing, we just stopped polling): stale ⇒ `distinct_navs <= 1` (flat) AND `oldest_age >= 90% of window` (window actually spanned — not a cold start) AND `max_gap <= 5 min` (continuously observed — no outage masquerading as a freeze). This also drops the strict-monotonicity assumption (a dip-and-recover shows `distinct >= 2`) AND fixes the cold-start-into-a-frozen-vault miss (a densely-observed flat window fires regardless of prior history). Anything thin/young/gappy fails OPEN. `perena.rs` now writes `intrinsic_liveness(USD*, stale, 'nav_accrual_stall', {distinct_navs, oldest_age_secs, max_gap_secs, poll_count, ...})` every poll (`postgres::perena_nav_window_stats` + the pure `nav_accrual_stale`), **fail-open** (missing stats / query error → not stale), observe-only until the gate is enabled. This is strictly better than the `backing_unverifiable` fallback that was on the table for an *unmeasurable* asset — USD\* turned out to be measurable. **Before ENABLE:** re-run the cadence query on fresh data (the standing "calibrate before flip" rule); 21d is 3 weekends but not a full quarter.
     - *(Kept for the truly-unmeasurable case:)* an asset with a genuinely flat/opaque backing (no epoch AND no monotonic accrual to lean on) should still get a zero-inference **`backing_unverifiable`** disclosure (ADR-0037 reason-code pattern) rather than a misfiring heuristic — but USD\* is not that case.
   - **✅ USD\* vs dSOL — RATIFIED: keep USD\* active (2026-07-18).** USD\* is `active=true` + public + alert-dispatching (`monitoring_only` stopped gating egress on 2026-06-16), i.e. the *same* "frozen backing reads as confident PEGGED" exposure that got **dSOL proactively deactivated** (mig 0020). The keep-active call was explicitly examined rather than assumed: **(1)** USD\* is now *covered* by `nav_accrual_stall` — the specific gap that made it dSOL-like (an uncovered frozen-backing blind spot) is closed, so once `INTRINSIC_LIVENESS_GATE` is enabled a frozen USD\* crank forces UNKNOWN rather than false-PEGGED; **(2)** unlike dSOL, USD\* has NO incident history (dSOL's urgency was Drift-exploit adjacency); **(3)** the gate is disabled-default fleet-wide, so *every* intrinsic-backed asset shares this exposure until it ships — singling out USD\* would be inconsistent; **(4)** USD\* is 1 of only 3 yield-stables in the public 37-asset lineup, so pulling it is a real product regression, not free. **Decision: USD\* stays active; the frozen-backing exposure is closed via coverage + the (disabled-default) gate, not deactivation.** Revisit only if USD\* shows incident history before the gate ships.
   - **Piggybank (pbUSDC) — DEACTIVATED, dormant gap. Model CORRECTED (2026-07-18).** `active=false` (mig 0040) → the source idles and writes nothing, so the gap cannot fire today. **Disposition unchanged: do NOT wire speculatively** (a deactivated asset writes nothing, the window is un-calibratable while it's off, and dead code for a dead asset is exactly what BUILD-TO-DEMAND avoids) — but the *reactivation checklist model was wrong and is now fixed*. Earlier text said "mirror `spl_stake_pool` with `epoch_lag >= 1`" — but that's the WRONG shape: `epoch_lag` needs an external "current epoch" to diff against (Solana's, for stake pools), and Piggybank's `epoch_id` is its OWN 48h protocol counter with no external clock. So pbUSDC is a **monotonic-counter stall**, exactly like the new Perena `nav_accrual_stall` — not an `epoch_lag`. **On reactivation:** mirror `perena.rs` — the same densely+continuously-observed FLAT-window check (`distinct <= 1` AND window-spanned AND `max_gap` small) over the pbUSDC crank counter (its decoded `epoch_id`, or equivalently its monotonic `nav`, since pbUSDC is also a monotonic-yield vault), with a stall window of **~96h** (2× the 48h epoch cadence) and its own `max_gap`, then **re-calibrate against live pbUSDC history the same way Perena was** before enabling. `reason='epoch_stall'` (or reuse `nav_accrual_stall`).
   - **Net (updated 2026-07-18):** Perena/USD\* is **now covered** (`nav_accrual_stall`, calibrated live), so the only remaining uncovered source is the **deactivated** pbUSDC — which idles + writes nothing, so there is no live gap at all today. Every writer fails OPEN and the gate is disabled-default, so nothing here is a live prod risk; the pbUSDC wiring stays deferred to its reactivation checklist (the corrected **monotonic-stall** model above, NOT `epoch_lag`).
