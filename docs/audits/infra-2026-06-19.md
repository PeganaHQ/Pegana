## Findings

### [MEDIUM] INFRA-01: GitHub Actions run without an explicit least-privilege `permissions:` block (4 of 5 workflows)
**Confidence:** 8/10 · **Phase:** 3 — CI/CD · **Category:** OWASP A05 (Misconfiguration) / A08 (Integrity)
**Location:** `.github/workflows/{ci,lighthouse,reproducible-build,web-e2e}.yml` (no `permissions:` at top level or job level)

**Description:** Four of five workflows declare no `permissions:` block, so their `GITHUB_TOKEN` inherits the repository default scope. `ci.yml` runs third-party actions (`Swatinem/rust-cache`, `oven-sh/setup-bun`, `dtolnay/rust-toolchain`); if the repo default is read/write, a compromised action could use the ambient token to tamper with repo contents, releases, or packages. The one workflow that genuinely needs write power — `sync-pegana-replay.yml` — **already** scopes itself correctly (`permissions: contents: read` at line 60, with the actual mirror push using a separate, narrowly-scoped PAT). So the highest-risk path is already locked down; this finding is defense-in-depth for the remaining four.

**Exploit scenario:**
1. A third-party action used in `ci.yml` (e.g. a tag-mutated `rust-cache`) is compromised.
2. With the default read/write `GITHUB_TOKEN`, its step can push a commit, create a release, or publish a package using the ambient token — no extra secret needed.
3. (Mitigated for the mirror push, which uses the read-only token + separate PAT.)

**Evidence:**
```
ci.yml                  ABSENT (default token scope)
lighthouse.yml          ABSENT
reproducible-build.yml  ABSENT
web-e2e.yml             ABSENT
sync-pegana-replay.yml  permissions: contents: read   ← already correct
```

**Remediation:** Add a top-level least-privilege block to the four workflows:
```yaml
permissions:
  contents: read   # elevate per-job only where a step needs write
```
(Optionally also set the repo-wide default to "read" in Settings → Actions → Workflow permissions.) **Priority:** P2 (this month).

> Relationship to prior audit: this supersedes the prior **F-14 (SHA-pin actions, CUT)** — for a private single-author repo, an explicit least-privilege `permissions:` block is a *more justified and cheaper* mitigation of the same "compromised third-party action" risk than SHA-pinning. Track as **F-42** in the remediation SPEC.
