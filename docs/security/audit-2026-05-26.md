## Executive summary

PEGANA is a Solana stablecoin/LST peg-monitoring stack ("risk oracle"): 6 Rust crates (indexer, engine, dispatcher, api, common, xtask), a Next.js 16 web console, and a Bun/grammY Telegram bot. **There are no on-chain programs** — PEGANA only reads Solana via RPC, so checklists 01–07 (Solana program safety) do not apply. The audit focused on backend security, supply chain, web XSS surface, bot auth, and operational posture.

**Overall posture is good.** SQLx parameterized queries throughout (no SQL injection), proper IDOR scoping on `/v1/me/*` via `telegram_id` joins, well-implemented Telegram-Login HMAC + JWT-with-revocation, Cargo.lock committed and `cargo build --locked` enforced in all Rust Dockerfiles, non-root containers (UID 10001), Caddy ships HSTS+nosniff+X-Frame-DENY+strict-origin+Permissions-Policy, helmet-equivalent escapeHtml on every interpolated value in bot messages, idempotency keys on alert sends, daily-digest janitor for unbounded tables. The team has clearly thought about security.

**Two findings rise to HIGH:**

- **F-001 (sev 7) — `bot-ts` supply chain is broken.** `bot-ts/bun.lock` is gitignored at `.gitignore:46` (`**/bun.lock`), and the Dockerfile's `COPY package.json bun.lockb* ./` uses the *binary-format* glob that does NOT match the *text-format* `bun.lock` the project actually uses. Both the Docker build and the CI `bun install --frozen-lockfile` run with no lockfile present — `--frozen-lockfile` is a placebo. Every bot release resolves dependencies fresh from the registry; a malicious version of any transitive dep (`grammy`, `pino`, `@grammyjs/i18n`, `postgres`, `zod`, `@sentry/node` and their trees) lands in production with no detection.

- **F-002 (sev 7) — Rate limiter is bypassed behind Caddy.** `crates/api-rs/src/rate_limit.rs:60-69` uses `ConnectInfo<SocketAddr>` (the TCP source IP). In production, every request arrives from Caddy's container IP, so the entire internet shares one 60/min bucket. The limiter is effectively off for every endpoint except `/healthz`/`/readyz`. Caddy forwards `X-Forwarded-For` by default but the Rust code never reads it.

The remaining MEDIUM findings (CORS `Any`, Redis no-password, internal-secret non-constant-time, weak min-length on `BOT_INTERNAL_SECRET`, no JWT secret length validation) are defense-in-depth issues — none are individually exploitable, but together they widen the lateral-movement surface.

## Findings

### [HIGH] F-001 — `bot-ts` supply chain has no lockfile in builds

| Field | Value |
|---|---|
| **Severity** | 7 — 🟠 HIGH |
| **Confidence** | 10/10 |
| **Phase** | 3 + 4 — Supply chain + CI/CD |
| **Category** | OWASP A03 (Supply-Chain Failures) |
| **Location** | `.gitignore:46`, `bot-ts/Dockerfile:3-4`, `.github/workflows/ci.yml:72` |

**Description**
Three independent factors compound:

1. Root `.gitignore` excludes `**/bun.lock` (line 46). The local `bot-ts/bun.lock` file exists (54 KB) but is never tracked by git — confirmed via `git ls-files bot-ts/`, which shows no `bun.lock` entry.
2. `bot-ts/Dockerfile:3` uses `COPY package.json bun.lockb* ./`. The glob `bun.lockb*` matches the **old binary format** (`bun.lockb`, `bun.lockb.json`). It does **not** match the current text format `bun.lock` that Bun 1.2+ produces. Verified locally — the pattern expands to itself (no match).
3. Both `bot-ts/Dockerfile:4` (`bun install --frozen-lockfile --production`) and `.github/workflows/ci.yml:72` (`bun install --frozen-lockfile`) run that command with no lockfile present in the build context.

The net effect: every CI run and every Docker build resolves the entire dependency tree fresh from npmjs.org. `--frozen-lockfile` is meant to fail when the lock disagrees with `package.json`, but with no lock at all, the flag does nothing.

**Impact**
- **No reproducibility:** two builds from the same commit can install different dependency versions.
- **No supply-chain audit trail:** there is no committed artefact showing which transitive versions shipped to production.
- **Silent dependency drift:** a malicious version published to any transitive (e.g., `pino-std-serializers`, `@sentry/core`, `@grammyjs/runner`'s deps) ships immediately to prod with no review.
- **`bun audit` is impossible** — there is no lockfile to audit against.

The bot writes to the production Postgres, sends alerts to users, and holds `BOT_TOKEN` + `BOT_INTERNAL_SECRET` + `DATABASE_URL` — a compromised dep can exfiltrate all three.

**Remediation**
1. Remove `**/bun.lock` from `.gitignore` and commit the current `bot-ts/bun.lock`.
2. In `bot-ts/Dockerfile:3`, change `COPY package.json bun.lockb* ./` to `COPY package.json bun.lock ./` (no glob, fail-loud if missing).
3. Add a `bun audit` step to `.github/workflows/ci.yml` after `bun install`.
4. (Optional) Add `bun pm pack --dry-run` or a hash check to CI to detect lockfile vs package.json drift.

**Priority:** P1 — fix this sprint. The fix is < 30 min.

### [HIGH] F-002 — Rate limiter uses TCP source IP, ineffective behind Caddy

| Field | Value |
|---|---|
| **Severity** | 7 — 🟠 HIGH |
| **Confidence** | 10/10 |
| **Phase** | 9 — Backend |
| **Category** | OWASP A04 (Insecure Design) / STRIDE Denial-of-Service |
| **Location** | `crates/api-rs/src/rate_limit.rs:60-74`, `crates/api-rs/src/main.rs:102-105` |

**Description**
The rate-limit middleware extracts the client address via `ConnectInfo<SocketAddr>` and indexes the bucket map by `addr.ip()`. In `docker-compose.yml`, the `caddy` service (lines 129-137) proxies all traffic to `api:8080`. From `api-rs`'s perspective, every request's TCP source is Caddy's internal docker-network IP (always the same address). All public traffic therefore lands in a single bucket — the 60-req/min cap is shared by the entire internet.

Caddy's `reverse_proxy` directive (Caddyfile:27, 29) forwards `X-Forwarded-For` by default, but `rate_limit.rs` never reads it.

**Impact**
- A single attacker can exhaust the global 60-req/min budget by sending 60 requests from any IP — every legitimate user then sees 429 for the rest of the window.
- The `pegana_api_rate_limited_total` metric will count the global cap being hit, not per-attacker abuse — operators can't distinguish a DoS from organic growth.
- Login endpoint `/v1/auth/telegram` (which does a DB upsert + DB write per call) is unprotected at the per-IP level — credential stuffing / replay-window abuse becomes a DB-amplification vector.

**Proof of concept** (illustrative; do not run in prod)
```bash
# From a single attacker box (one IP)
for i in $(seq 1 60); do curl -s -o /dev/null https://api.pegana.xyz/v1/assets; done
# Subsequent requests from any other IP now return 429 until the window resets.
```

**Remediation**
Use `tower_governor` or a custom extractor that reads `X-Forwarded-For`/`X-Real-IP` (the first value, validated against a trusted-proxy allowlist that includes the Caddy container's IP range). Caddy already sets these by default; the change is one extractor plus one allowlist constant.

Sketch:
```rust
fn client_ip(req: &Request) -> IpAddr {
    if let Some(h) = req.headers().get("x-forwarded-for")
        .and_then(|v| v.to_str().ok())
    {
        if let Some(first) = h.split(',').next().map(str::trim) {
            if let Ok(ip) = first.parse() { return ip; }
        }
    }
    req.extensions().get::<ConnectInfo<SocketAddr>>()
        .map(|c| c.0.ip()).unwrap_or(IpAddr::V4(Ipv4Addr::UNSPECIFIED))
}
```

**Priority:** P1 — fix this sprint.

### [MEDIUM] F-003 — CORS `allow_origin: Any` on production API

| Field | Value |
|---|---|
| **Severity** | 6 — 🟡 MEDIUM |
| **Confidence** | 9/10 |
| **Phase** | 9 — Backend |
| **Category** | OWASP A05 (Security Misconfiguration) |
| **Location** | `crates/api-rs/src/main.rs:52-65` |

**Description**
The API permits any origin to send requests, including with the `Authorization` header:

```rust
let cors = CorsLayer::new()
    .allow_methods([GET, POST, PATCH, DELETE])
    .allow_origin(Any)
    .allow_headers([CONTENT_TYPE, AUTHORIZATION]);
```

`allow_credentials` is not set, so cookies are not sent cross-origin — that's why this is medium and not high. But:

- The JWT is stored in `localStorage` (`web/lib/auth/context.tsx:67`), not in a cookie.
- If an attacker obtains a JWT (via XSS, malicious browser extension, shared device, dev-tools screenshot, leaked Sentry breadcrumb), they can call the API from any origin — there is no origin discipline.
- The web/`lib/auth/context.tsx:5-13` comment explicitly documents the trade-off ("XSS exposure accepted because the web has no user-generated content"). The CORS-`Any` choice removes the *second* line of defense.

**Impact**
- Cross-origin Bearer-token replay attacks become trivial once a token leaks.
- Phishing pages can call `pegana.xyz` API directly to enumerate which Telegram IDs are valid (`/v1/me` returns 200 for valid token).

**Remediation**
Whitelist the production origins:
```rust
.allow_origin(AllowOrigin::predicate(|origin, _| {
    matches!(origin.to_str().ok(), Some(
        "https://pegana.xyz" | "https://www.pegana.xyz" | "http://localhost:3000"
    ))
}))
```

**Priority:** P2 — fix within 2 weeks.

### [MEDIUM] F-004 — Redis instance has no authentication

| Field | Value |
|---|---|
| **Severity** | 6 — 🟡 MEDIUM |
| **Confidence** | 10/10 |
| **Phase** | 4 + 5 — Infrastructure |
| **Category** | OWASP A05 / STRIDE Tampering + Elevation |
| **Location** | `docker-compose.yml:16-25` |

**Description**
The `redis` service runs with no `--requirepass`:
```yaml
redis:
  image: redis:7-alpine
  command: ["redis-server", "--save", "60", "1", "--appendonly", "yes"]
```

Inside the docker network, any container can connect to `redis:6379` and execute arbitrary Redis commands — including `FLUSHALL`, `CONFIG SET`, `PUBLISH` on the engine's `pegana:discount` channel, or subscribing to read all alert data in real time.

`redis:6379` is not port-mapped to the host (good), so internet exposure is not the issue. The threat model is **lateral movement**: a compromise of any single container (indexer, engine, dispatcher, api, bot) yields full Redis control, which then yields:

- **Inject false discount updates** to all connected WebSocket clients (`crates/api-rs/src/ws.rs:131-173` forwards any well-shaped `kind: "update"` payload).
- **Suppress real updates** by repeatedly publishing fake heartbeats so the engine appears alive while the attacker silences alerts.
- **Replay or modify pub/sub history** if persistence is enabled (it is — `--appendonly yes`).

**Impact**
A compromised bot dep (see F-001) gives the attacker pub/sub control of the live alert stream. Subscribers see "all assets healthy" while peg actually breaks — directly defeats PEGANA's product purpose.

**Remediation**
1. Set `REDIS_URL=redis://default:${REDIS_PASSWORD}@redis:6379` in `.env` (and `.env.example`).
2. In `docker-compose.yml`:
   ```yaml
   redis:
     command: ["redis-server", "--requirepass", "${REDIS_PASSWORD:?required}",
               "--save", "60", "1", "--appendonly", "yes"]
   ```
3. Document `REDIS_PASSWORD` in `docs/ops/deploy-hetzner.md`.

**Priority:** P2 — fix within 2 weeks.

### [MEDIUM] F-005 — `bot-ts` internal-secret comparison is not constant-time

| Field | Value |
|---|---|
| **Severity** | 5 — 🟡 MEDIUM |
| **Confidence** | 10/10 |
| **Phase** | 11 — Bot security |
| **Category** | Cryptographic best practice |
| **Location** | `bot-ts/src/index.ts:609` |

**Description**
```typescript
if (req.headers.get("x-internal-secret") !== env.BOT_INTERNAL_SECRET) {
  return new Response("unauthorized", { status: 401 });
}
```

JavaScript `!==` on strings short-circuits at the first byte mismatch, leaking secret length and per-byte timing. The endpoint is on `bot:3000`, only reachable from inside the docker network — threat model is a compromised peer container, not the internet. Still, defense-in-depth.

**Remediation**
Use `crypto.timingSafeEqual` (Bun supports it via `node:crypto`):
```typescript
import { timingSafeEqual } from "node:crypto";
const provided = req.headers.get("x-internal-secret") ?? "";
const a = Buffer.from(provided);
const b = Buffer.from(env.BOT_INTERNAL_SECRET);
if (a.length !== b.length || !timingSafeEqual(a, b)) {
  return new Response("unauthorized", { status: 401 });
}
```

**Priority:** P2 — fix within 2 weeks.

### [MEDIUM] F-006 — `BOT_INTERNAL_SECRET` minimum length only 8 characters

| Field | Value |
|---|---|
| **Severity** | 5 — 🟡 MEDIUM |
| **Confidence** | 10/10 |
| **Phase** | 12 — Secrets |
| **Location** | `bot-ts/src/index.ts:70` |

**Description**
```typescript
BOT_INTERNAL_SECRET: z.string().min(8),
```

8 characters of arbitrary printable input have at best ~52 bits of entropy. For a shared secret that authenticates a service-to-service POST endpoint, this is well below the 128-bit floor recommended for HMAC-equivalent secrets.

**Remediation**
```typescript
BOT_INTERNAL_SECRET: z.string().min(32, "BOT_INTERNAL_SECRET must be ≥32 chars (use `openssl rand -hex 32`)"),
```

Update `.env.example` accordingly.

**Priority:** P2 — fix within 2 weeks.

### [MEDIUM] F-007 — No JWT secret length validation at API startup

| Field | Value |
|---|---|
| **Severity** | 5 — 🟡 MEDIUM |
| **Confidence** | 10/10 |
| **Phase** | 9 — Backend auth |
| **Location** | `crates/api-rs/src/auth/mod.rs:18-27` |

**Description**
```rust
impl AuthConfig {
    pub fn new(bot_token: &str, jwt_secret: &str) -> Self {
        ...
        jwt_secret: jwt_secret.as_bytes().to_vec(),
    }
}
```

`AuthConfig::new` accepts any byte length. `.env.example` recommends `openssl rand -hex 32` in a comment, but the code does not enforce it. If an operator copy-pastes a short value (or the env parser fails and leaves the field default-empty), HS256 signing degrades to trivially brute-forceable.

**Remediation**
```rust
pub fn new(bot_token: &str, jwt_secret: &str) -> Result<Self, &'static str> {
    if jwt_secret.len() < 32 {
        return Err("JWT_SECRET must be at least 32 bytes");
    }
    ...
}
```
And propagate the error in `main()` so the API refuses to start with a weak secret.

**Priority:** P2 — fix within 2 weeks.

### [LOW] F-008 — Telegram-Login HMAC comparison not constant-time

| Field | Value |
|---|---|
| **Severity** | 4 — 🔵 LOW |
| **Confidence** | 9/10 |
| **Phase** | 9 — Backend auth |
| **Location** | `crates/api-rs/src/auth/telegram.rs:75-79` |

**Description**
```rust
let expected_hex = hex::encode(expected);
if expected_hex != payload.hash.to_ascii_lowercase() {
    return Err(LoginError::BadHash);
}
```

256-bit HMAC makes brute-force-via-timing infeasible in practice; flagged as defense-in-depth.

**Remediation**
Replace `finalize() + hex::encode + string compare` with `mac.verify_slice(&claim_hash_bytes)`, which `hmac` implements in constant time.

**Priority:** P3 — backlog.

### [LOW] F-009 — WebSocket endpoint has no origin check or per-IP connection limit

| Field | Value |
|---|---|
| **Severity** | 4 — 🔵 LOW |
| **Confidence** | 9/10 |
| **Phase** | 9 — Backend |
| **Location** | `crates/api-rs/src/ws.rs:54-87` |

**Description**
`/v1/ws` accepts upgrade with no `Origin` validation and no concurrent-connection cap. Each accepted client opens a dedicated Redis pub/sub subscriber (line 68). The rate limiter (F-002) counts the upgrade HTTP request once but does not constrain how many simultaneous WS connections one IP holds open.

**Impact**
A connection-flood attack from a small number of IPs can exhaust the Redis client connection pool, denying live updates to legitimate users. Data is public (peg health) so there is no confidentiality issue.

**Remediation**
1. Check `Origin` header on upgrade and reject anything not in the pegana.xyz allowlist (same set as F-003).
2. Track active connections per IP in `AppState` and reject new opens above a small N (e.g., 5).

**Priority:** P3 — backlog.

### [LOW] F-011 — No CSP header on Caddy responses

| Field | Value |
|---|---|
| **Severity** | 3 — 🔵 LOW |
| **Confidence** | 9/10 |
| **Phase** | 4 — Infrastructure |
| **Location** | `Caddyfile:14-21` |

| Field | Value |
|---|---|
| **Severity** | 3 — 🔵 LOW |
| **Confidence** | 10/10 |
| **Phase** | 3 — Supply chain |
| **Location** | All Dockerfiles + `docker-compose.yml` |

### [INFO] F-013 — JWT stored in localStorage (acknowledged design choice)

| Field | Value |
|---|---|
| **Severity** | 2 — ⚪ INFO |
| **Phase** | 10 — Frontend |
| **Location** | `web/lib/auth/context.tsx:5-13, 67` |

**Description**
The team has explicitly documented this trade-off:
> "Why localStorage over httpOnly cookie: simplifies the api-rs surface (no cookie config, no CORS credentials negotiation, no CSRF protection). The tradeoff is XSS exposure — accepted because the web has no user-generated content rendered as HTML in v1.1."

This is a defensible decision in v1.1. Two follow-ups for v1.2+:

1. **Future-proofing:** if any feature ever renders user content (comments, profile bios, custom alert labels), a strict CSP becomes mandatory. Add `Content-Security-Policy` headers via Next.js middleware before that point.
2. **The decision interacts with F-003** — open CORS amplifies the impact of any JWT leak.

**Priority:** P3 — track in roadmap.
